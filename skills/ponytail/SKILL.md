## 目的

実装前の設計から、不要な機能、重複実装、不要な依存、過剰な抽象化を削る。
機能を失わずに最小の設計へ絞り、実装者の裁量で余計なコードが増える余地を減らす。

## 行動理念

以下を上から順に適用する:

- これはそもそも必要か。必要性が疑わしい場合は省略し、その旨を一行で述べる（YAGNI）
- 既にこのコードベースに存在するものはないか。既存の helper、utility、型、pattern を記述前に確認して再利用する。数ファイル離れた場所にあるものを再実装するのは、最もよくある手抜きである
- 標準 library にその機能があるなら、それを使う
- native platform 機能でカバーできないか。picker library より `<input type="date">`、JS より CSS、application code より DB constraint を優先する
- 既に導入済みの依存関係で解決できるなら、それを使う。数行で済む処理のために新しい依存関係を追加しない
- 一行でいいなら、一行で書く

この順序は、新しい abstraction や依存関係を正当化する checklist ではない。より上の選択肢で解決できた時点で、下の選択肢を検討しない。

## 境界

- 対象は `draft-prompt/` の未承認ドラフトだけとする
- 本体コード、テスト、設定、依存関係、`.[agent_name]/prompt/` を変更しない
- compose-prompt の必須ファイル構成と必須 section を壊さない
- ユーザーが design-preflight で明示的に受け入れた要件や trade-off を、単純化だけを理由に覆さない
- 単純化で挙動、security、data integrity、互換性が変わる場合は勝手に変更せず、判断が必要な論点として返す

## 調査の委任

既存実装、標準機能、native機能、導入済み依存の調査は、DeepSeek など利用可能な下位モデルの読み取り専用 subagent へ委任する。上位モデルは調査項目の設計、候補の比較、採否判断、ドラフト修正に集中する。

1. 設計書ごとに「不要性」「既存実装」「標準・native機能」「導入済み依存」の探索項目を作る
2. 独立した項目は下位モデルへ並行委任する
3. `file:line`、再利用候補の実際の契約、適用できない理由、未確認事項を返させる
4. 上位モデルが採用する候補の根拠だけを実ファイルで再確認する
5. 下位モデルの提案を、そのまま設計へ採用しない

下位モデルへドラフトの変更を許可しない。探索結果を受けて設計を変える責任は上位モデルが持つ。

## 実行フロー

### Step 1: 入力を確認する

`draft-prompt/.prompt.md` と、そこから参照される `branch-*-prompt.md` を対象にする。ドラフトが存在しない、index と設計書が対応しない、または既に正式反映済みの場合は変更せず停止する。

design-preflight の確定要件、受け入れた副作用、未確認事項が現在の会話にある場合は、それを制約として使う。

### Step 2: 削れる仮説を作る

各 Summary / Changes / 対象ファイルについて次を問う:

1. 要件達成に本当に必要か
2. 既存機能と重複していないか
3. 新設予定の helper、utility、型、component、endpoint を既存要素で置き換えられないか
4. library や application code を標準・native機能へ置き換えられないか
5. 新しい依存関係を導入済み依存または短い直接実装で消せないか
6. 分岐、loop、error処理、副作用を失わず、より短く明確に書けないか

### Step 3: 仮説をコードベースで検証する

Step 2 の探索を下位モデルへ委任する。名前の一致だけで再利用可能と判断せず、引数、戻り値、副作用、error、利用範囲が要件と一致するか確認する。

標準・native機能は対象 runtime、browser support、database、framework version で利用可能か確認する。導入済み依存は lockfile だけでなく、実際の利用 pattern と保守境界も確認する。

### Step 4: ドラフトを単純化する

確認できた根拠だけを使い、`draft-prompt/` を次のように修正する:

- 不要な機能、対象ファイル、処理を削る
- 新設予定の要素を、既存実装の再利用へ置き換える
- 独自実装を標準・native機能へ置き換える
- 不要な新規依存を消す
- 同じ意味を保てる疑似コードを最小行数へ縮める
- 設計書全体が不要なら index と設計書を両方対象から外す

Summary / Changes / 対象ファイル / 参照ルール / 完了条件の必須 section は維持する。短さのために error処理、副作用、data integrity、security条件を省略しない。

### Step 5: 変更を報告する

省略または置換した項目ごとに、理由と根拠を一行で報告する。長い一般論は書かない。

```
- <省略・置換したもの>: <一行の理由>（根拠: path/to/file:line）
```

判断が必要で変更しなかった項目は、選択肢、挙動差、推奨を meeting へ返す。ユーザーへ直接質問しない。

### Step 6: meeting へ戻す

結果を次の status とともに meeting へ返す:

- `ponytail_ready`: 現在の draft revision を単純化し、未決定事項がない
- `consultation_required`: 挙動を変える候補があり、ユーザー判断が必要
- `blocked`: ドラフトの不整合、委任失敗、根拠不足により続行できない

ponytail は正式反映を行わない。meeting がユーザーの最終承認を得た後だけ、compose-prompt の `apply` mode へ進む。
